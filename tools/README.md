# Как посмотреть базу в DBeaver

База Sprout — обычный **SQLite**, и DBeaver открывает его напрямую. PostgreSQL для этого не нужен.

```powershell
.\tools\pull-db.ps1
```

Скрипт положит рядом `sprout-snapshot.db`. Дальше в DBeaver: **Новое соединение → SQLite → указать этот файл**. Драйвер DBeaver предложит скачать сам, интернет нужен один раз.

## Что важно понимать

**Это снимок, а не живое соединение.** Файл лежит внутри приложения на телефоне, и DBeaver туда не дотянется. Каждый раз, когда хочется свежих данных, скрипт надо запустить заново.

**Room пишет через WAL.** Часть свежих записей живёт не в самом `sprout.db`, а в соседнем `sprout.db-wal`. Скопировать один файл и получить неполную базу — легко, и ошибка молчаливая: снимок откроется, просто окажется старым. Поэтому скрипт сначала делает `wal_checkpoint`.

**Работает только с debug-сборкой.** `run-as` пускает в приватную папку приложения, потому что сборка помечена отлаживаемой. С релизной из Google Play это не сработает — и так и должно быть.

## Что где лежит

| Таблица | Что внутри |
|---|---|
| `tasks` | Задачи: название, первый шаг, план «если — то», напоминание |
| `events` | Всё, что происходило. Никогда не редактируется — на этом стоит вся будущая аналитика |
| `sessions` | Фокус-сессии: план, факт, паузы, оценка |
| `garden` | Одна строка: очки роста, серия, заморозки |
| `grown_plants` | Выросшие растения |

Полезно начать отсюда:

```sql
select datetime(at/1000, 'unixepoch', 'localtime') as когда, type, taskId, payload
from events
order by at desc;
```

## Без выгрузки файла

Если нужно быстро глянуть одну цифру, ходить в DBeaver необязательно — `sqlite3` есть прямо на устройстве:

```powershell
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb shell "run-as com.sprout.focus sqlite3 databases/sprout.db 'select type, count(*) from events group by type;'"
```

Приложение при этом лучше погасить: пока оно держит базу, запись упрётся в `database is locked`, а правки снаружи Room всё равно не увидит до перезапуска.

**Кавычки внутри такой команды съедаются шеллом устройства.** `where type='task_postponed'` доедет как `where type=task_postponed`, и sqlite отругается на несуществующую колонку. Для запросов со строками и для всего кириллического — файлом:

```powershell
$sql = "select count(*) from events where type='task_postponed';"
[System.IO.File]::WriteAllText("$env:TEMP\q.sql", $sql, (New-Object System.Text.UTF8Encoding($false)))
& $adb push "$env:TEMP\q.sql" /data/local/tmp/q.sql
& $adb shell "cat /data/local/tmp/q.sql | run-as com.sprout.focus sqlite3 databases/sprout.db"
```

## Демо-история для проверки экрана «Я»

Наблюдения показываются только при достаточном объёме данных, поэтому на живой базе первых дней проверять там нечего.

```powershell
.\tools\seed-history.ps1            # месяц правдоподобных данных
.\tools\seed-history.ps1 -Restore   # вернуть базу, какой она была
```

Перед записью снимается копия в `tools\sprout-before-seed.db` — скрипт дописывает в ту же базу, где лежат настоящие задачи, а восстановить их неоткуда.

Проверять экран стоит **на обоих** состояниях. На подложенной истории он выглядел безупречно; настоящая бедная база тут же показала «2 раз из 5» без склонения и вывод, сделанный из двух случаев.
